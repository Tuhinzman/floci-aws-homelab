# v0.7 Full Ubuntu VM Reboot Validation

## Status

**PASS**

Validation time: 2026-08-31 UTC / 2026-08-30 EDT

This test answers a simple question: if the Ubuntu VM is rebooted, does the lab recover by itself and can the existing event-driven workflow process a new message without rebuilding anything?

The answer in the reference lab was yes.

This record is sanitized. It does not include the private VM address, event-source mapping UUID, SQS message ID, generated order ID, container ID, or raw command logs.

## What existed before the reboot

Before restarting the VM, the following checks passed:

```text
Docker service enabled             PASS
Docker service active              PASS
Floci container running            PASS
Floci health                       healthy
Floci restart policy               unless-stopped
Manual SQS queue                   present
Manual DynamoDB table              ACTIVE
Manual Lambda function             Active
Manual event-source mapping        Enabled
```

The queue URL and event-source mapping UUID were saved locally so the same resources could be compared after the reboot.

## Reboot recovery

The Ubuntu VM was rebooted normally.

After reconnecting, the system reported a fresh boot. Docker had started automatically, and Floci was already healthy on the first health check.

Observed checks:

```text
DOCKER_ENABLED_AFTER_REBOOT=PASS
DOCKER_ACTIVE_AFTER_REBOOT=PASS
FLOCI_AUTO_START_AFTER_REBOOT=PASS
FLOCI_HEALTH_AFTER_REBOOT=PASS
```

## Resource persistence

The manual reference stack was then compared with the pre-reboot baseline.

The same queue and event-source mapping were still present, and the application resources were ready:

```text
QUEUE_IDENTITY_AFTER_REBOOT=PASS
DYNAMODB_AFTER_REBOOT=PASS
LAMBDA_AFTER_REBOOT=PASS
MAPPING_UUID_AFTER_REBOOT=PASS
MAPPING_STATE_AFTER_REBOOT=PASS
```

This is stronger than only checking that Floci restarted. It confirms that the tested application resources survived the guest operating-system reboot.

## Functional test after the reboot

A new SQS message was sent after the reboot.

The first validation attempt reached the message-send step successfully but stopped while a helper Python command tried to parse the DynamoDB response as JSON. The failure was in the validation parser, not in the recovered infrastructure.

The VM was not rebooted again and the resources were not recreated. The validation resumed in the same post-reboot session using AWS CLI `--query` field reads instead of the Python JSON helper.

A new message was sent. The new DynamoDB item appeared on the second poll.

The following exact values were checked:

```text
status       = created
source       = sqs-lambda
processed_by = floci-orders-processor
message_id   = exact ID returned by SQS
```

Observed assertions:

```text
SQS_MESSAGE_SEND=PASS
DYNAMODB_STATUS_ASSERTION=PASS
DYNAMODB_SOURCE_ASSERTION=PASS
DYNAMODB_PROCESSOR_ASSERTION=PASS
DYNAMODB_MESSAGE_ID_ASSERTION=PASS
```

## Docker-backed Lambda after reboot

The post-reboot message created a running Docker-backed Lambda runtime. The runtime container was also verified on the expected Compose network.

```text
LAMBDA_CONTAINER_RUNNING=PASS
LAMBDA_CONTAINER_NETWORK=PASS
```

Final result:

```text
FLOCI_FULL_VM_REBOOT_VALIDATION=PASS
```

## What this proves

For the tested reference lab, a normal Ubuntu VM reboot preserved and recovered:

- Docker service startup
- Floci automatic startup and health
- the manual SQS queue
- the manual DynamoDB table
- the manual Lambda function
- the same event-source mapping identity and enabled state
- Docker-backed Lambda execution
- the SQS → Lambda → DynamoDB workflow with a new message after reboot

No application resources had to be recreated after the VM came back.

## What this does not prove

This test does not prove:

- recovery after a full Proxmox host reboot
- recovery after abrupt power loss
- real AWS IAM enforcement
- exact AWS retry or dead-letter queue behavior
- exactly-once processing
- production scaling, high availability, or performance
- full compatibility with every AWS API

Those remain outside the current validation boundary.
