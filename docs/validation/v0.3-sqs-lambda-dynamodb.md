# v0.3 SQS to Lambda to DynamoDB Validation

## Status

**PASS**

Validation date: 2026-08-30

This record documents the first complete event-driven workflow validated in the homelab:

```text
SQS message
→ Lambda event-source mapping
→ Docker-backed Lambda execution
→ DynamoDB write
→ exact item read-back
```

The record is sanitized. It does not include the private VM address, MAC address, SSH material, machine identifiers, Docker container ID, event-source mapping UUID, order ID, or message ID from the original run.

## Workflow executed

The repository script `scripts/smoke-test-sqs-lambda-dynamodb.sh` performed the following steps:

1. verified the local STS account
2. created the DynamoDB table `FlociOrders`
3. verified that the table reached `ACTIVE`
4. created the SQS queue `floci-orders-events`
5. read the queue ARN back and asserted its exact value
6. created the Lambda execution-role reference
7. attached an inline policy for the queue and table operations used by the function
8. packaged the Python event processor
9. removed any previous test mapping and function with the same names
10. created the Lambda function `floci-orders-processor`
11. waited for the function to become `Active`
12. created an SQS event-source mapping with batch size `1`
13. waited for the mapping to become `Enabled`
14. sent a uniquely identified order message to SQS
15. polled DynamoDB for the resulting item
16. asserted the exact item fields
17. read the event-source mapping and DynamoDB item back through the APIs
18. inspected the Lambda runtime container and Docker network

A unique message was sent to the queue. The DynamoDB item appeared on the second read attempt, showing that the asynchronous workflow completed successfully.

The item contained the expected fields:

```text

message_id   = SQS message ID returned by the send operation
processed_by = floci-orders-processor
```

The test asserted the values rather than only checking that an item existed.

## Verified claim boundary

This validation supports the following claims:

- an SQS queue can be created and read back through Floci
- a Lambda event-source mapping can connect the tested SQS queue to the tested function
- the mapping can reach the `Enabled` state
- an SQS message can trigger asynchronous Lambda execution
- the Lambda handler can call the local DynamoDB endpoint
- the handler can write the expected item to DynamoDB
- the item can be read back and its exact fields asserted
- the workflow uses a real Docker-backed Python Lambda runtime
- the runtime container joins the Floci Compose network

This validation does **not** yet prove:

- persistence of the Lambda function or event-source mapping across a Floci restart
- successful processing after a full VM reboot
- retry behavior after handler failure
- dead-letter queue behavior
- partial batch failure handling
- duplicate-delivery or exactly-once guarantees
- concurrency and scaling behavior
- real AWS IAM authorization enforcement
- CloudWatch Logs parity
- production AWS availability or performance

## Next bounded milestone
