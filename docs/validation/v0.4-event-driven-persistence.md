# v0.4 Event-Driven Restart Persistence Validation

## Status

**PASS**

Validation date: 2026-08-30

This record documents persistence of the complete tested event-driven workflow across a Floci container restart:

```text
existing SQS queue, Lambda function, event-source mapping, and DynamoDB table
→ restart Floci
→ read the same resources back
→ send a new SQS message
→ execute Lambda in Docker
→ write a new DynamoDB item
→ assert the exact item fields
```

The record is sanitized. It does not include the private VM address, MAC address, SSH material, machine identifiers, Docker container ID, event-source mapping UUID, message ID, or generated order ID from the original run.

## Preconditions

The following resources had already been created and validated by the v0.3 workflow:

- SQS queue `floci-orders-events`
- DynamoDB table `FlociOrders`
- Lambda function `floci-orders-processor`
- an enabled SQS event-source mapping with batch size `1`
- Python 3.13 Lambda runtime image `public.ecr.aws/lambda/python:3.13`

Before restart, the test read back:

```text
queue URL        = expected internal Floci URL
queue ARN        = expected local AWS-style ARN
table state      = ACTIVE
function state   = Active
mapping state    = Enabled
mapping UUID     = present
```

## Restart workflow

The repository script `scripts/validate-event-driven-persistence.sh` performed the following work:

1. read the queue URL and ARN
2. read the DynamoDB table state
3. read the Lambda function state
4. read the event-source mapping UUID and state
5. restarted the Floci container through the repository Compose configuration
6. waited for the Floci container to become healthy
7. read the same resources again
8. asserted that the queue URL and ARN were unchanged
9. asserted that the DynamoDB table remained `ACTIVE`
10. asserted that the Lambda function remained `Active`
11. asserted that the event-source mapping retained the same UUID
12. asserted that the mapping remained `Enabled`
13. sent a new uniquely identified SQS message
14. waited for a new DynamoDB item
15. asserted the new item fields
16. inspected the Docker-backed Lambda runtime after restart
17. asserted that the runtime container was running and attached to `floci_default`

## Verified claim boundary

This validation supports the following claims:

- the tested SQS queue survives a Floci container restart
- the tested DynamoDB table survives a Floci container restart
- the tested Lambda function survives a Floci container restart
- the tested event-source mapping survives with the same UUID
- the mapping remains enabled after restart
- a new SQS message triggers a new Docker-backed Lambda execution after restart
- the post-restart Lambda execution writes the expected DynamoDB item
- the exact item fields can be read back and asserted
- the post-restart Lambda runtime joins the Floci Compose network

This validation does **not** prove:

- persistence across a full Ubuntu VM or Proxmox host reboot
- retry and dead-letter queue behavior
- partial batch failure handling
- duplicate-delivery or exactly-once guarantees
- concurrency or scaling behavior
- real AWS IAM authorization enforcement
- production AWS availability, performance, or API parity
