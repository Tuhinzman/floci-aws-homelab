## Lambda workflow executed

The repository script `scripts/smoke-test-lambda.sh` performed the following steps:

1. created a temporary Python source file
2. packaged the function as a ZIP archive
3. created a local IAM execution role with a Lambda trust policy
4. read the role ARN back through the IAM API
5. created a Lambda function using runtime `python3.13`
6. waited for the function state to become `Active`
7. invoked the function synchronously with a JSON event
8. read the invocation metadata and function response
9. asserted status code `200`
10. asserted that no `FunctionError` was returned
11. asserted the exact response message
12. asserted that the input event reached the function unchanged
13. inspected the Docker runtime container
14. asserted that the runtime container was running
15. asserted that it was attached to `floci_default`
16. read the final Lambda configuration back through the API

## Function used for validation

The function returned a small JSON document containing:

- a fixed message
- the event received by the handler
- the function name supplied through the Lambda context

The invocation event identified the request as the repository Lambda smoke test. No credentials, private addresses, or real secrets were placed in the function package or payload.

## Network issue resolved during this milestone

Docker-spawned Lambda containers need a hostname that resolves inside the Compose network. The deployment therefore uses:

```text
FLOCI_INTERNAL_HOSTNAME=floci
```

That setting also changes absolute service URLs returned by Floci. The SQS persistence check was updated to expect the internal form:

```text
http://floci:4566/000000000000/<queue-name>
```

The workstation and VM shell still use the private VM address through the `aws-floci` wrapper.

## Verified claim boundary

This validation supports the following claims:

- a Python 3.13 Lambda function can be packaged and created through Floci
- a Lambda execution-role reference can be created and read back through the emulated IAM API
- the function can be invoked synchronously
- the request event reaches the function unchanged
- the response can be read back and asserted
- Floci creates a real Docker Lambda runtime container
- the runtime container uses the expected image
- the runtime container joins the Floci Compose network

This validation does **not** yet prove:

- Lambda function persistence across a Floci restart
- SQS or DynamoDB event-source mappings
- asynchronous invocation behavior
- retry and dead-letter behavior
- Lambda concurrency controls
- Lambda layers
- VPC-attached Lambda behavior
- CloudWatch Logs parity
- AWS IAM authorization parity
- production performance, scaling, or availability
